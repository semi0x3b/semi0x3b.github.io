EKS에서 OKE로 #1 — 크레딧에서 시작된 이관, 설계와 dev 구축기

EKS에서 OKE로 #1 — 크레딧에서 시작된 이관, 설계와 dev 구축기

2026년 7월 27일25 min read

올해 회사에 Oracle Cloud 크레딧이 생겼고, AWS의 관리형 쿠버네티스인 EKS에서 OCI의 관리형 쿠버네티스인 OKE로 서비스 전부를 옮기기로 했어요. 그런데 옮길 대상인 EKS에는 인프라 코드도 구축 히스토리도 없어서, 이 일은 “옮기기”이기 전에 “알아내기”였죠. 이 글은 dev 클러스터 하나를 Terraform으로 처음부터 짓는 동안 계정 구조를 뒤집은 뒤 내린 설계 결정 네 개와, 그 목록에 없던 함정들의 기록이에요.

거창한 기술적 서사로 시작하고 싶지만, 많은 회사의 클라우드 이관이 그렇듯 시작은 계약이었어요. 엔지니어링은 그다음이었고요. 1편인 이 글에서는 설계가 뒤집힌 과정과 dev 클러스터에서 밟은 함정들을 다루고, prod 이관과 컷오버는 2편에서 이어가요.

코드가 없는 EKS에서 출발했어요

출발선부터 옮길 대상을 아무도 설명해주지 못했어요. 기존 EKS는 오래전에 구축만 된 상태였거든요. 누가 왜 이렇게 만들었는지 히스토리가 없고 인프라 코드도 없었어요. 콘솔에 떠 있는 클러스터가 유일한 문서였죠. 돌아가는 클러스터를 실측해 사양을 역산하는 일이 이관 내내 따라다녀요. OKE를 처음부터 끝까지 Terraform으로 구축한 것도 같은 이유예요. 이번에는 코드가 곧 문서가 되도록요.

첫 타자는 신규 서비스인 채용 시스템이었어요. 4월에 이 서비스용 OCI 인프라를 설계하면서 새 플랫폼을 검증하고 기존 서비스는 그다음에 옮기는 순서였죠. 이 글의 dev 구축은 그 첫 타자용 플랫폼이 전사 이관의 기반으로 자라는 과정이에요.

어디에 지을지를 6일 만에 뒤집었어요

가장 먼저 정한 건 클러스터 사양이 아니라 계정 구조였어요. OCI에는 테넌시라는 최상위 계정 단위가 있어요. AWS 계정 하나에 해당해요. 처음에는 테넌시를 새로 만드는 안으로 잡았다가, 6일 만에 기존 테넌시를 확장하는 쪽으로 방향을 바꿨어요. 리전도 춘천에서 서울로 함께 옮겼어요. 이때 미리 써뒀던 dev용 네트워크·클러스터 정의를 걷어내고 당분간은 기존에 돌아가던 클러스터를 참조하는 구조로 갔어요. 이 선택이 뒤에 자원 목록을 다시 채워야 하는 일로 이어져요.

컨테이너 레지스트리나 메일 발송처럼 환경과 무관한 자원은 공용 compartment로 분리했어요. compartment는 테넌시 안에서 리소스를 묶어 격리하는 논리 단위인데, 폴더에 가까워요.

최종 설계는 이렇게 정리됐어요.

  • 테넌시는 기존 것 하나를 확장하고, 리전은 서울로 뒀어요
  • compartment는 8개예요. 환경별로 셋을 두고 나머지는 서비스별로 나눴어요
  • 예산은 월 $1,000에 70·90·100% 알림을 걸어뒀어요

dev 클러스터는 이렇게 채웠어요

네트워크는 VCN 하나(10.0.0.0/16)에 용도별 서브넷 넷을 뒀어요.

worker 서브넷에서 노드와 pod가 IP를 함께 쓴다는 게 나중에 발목을 잡아요. OKE의 VCN-native 네트워킹에서는 pod가 노드와 같은 서브넷에서 IP를 하나씩 받아가거든요. /24로 쓸 수 있는 IP는 251개뿐이라, 노드당 상한을 올리려 할 때 이 숫자가 먼저 막아서요. 그게 2편의 슬롯 이야기로 이어져요.

클러스터 자체는 이렇게 잡았어요.

  • 쿠버네티스는 v1.35.2를 쓰고, 워커는 VM.Standard.E4.Flex 2 OCPU / 16GB 3대로 시작했어요(지금은 6대예요)
  • 노드당 pod 상한은 31이에요. OCPU 수가 정하는 VNIC 개수에서 나온 값이거든요
  • boot volume은 100GB예요. 처음엔 50GB로 잡았다가 뒤에 나올 이유로 늘렸어요

클러스터 안은 서비스군 다섯 개를 네임스페이스로 나눠 담았어요. 기존 플랫폼과 채용·SaaS·커뮤니티·부트캠프인데, 가장 큰 곳이 31종이고 나머지는 7~8종씩이에요.

관문인 Kong은 기본 이미지가 아니라 토큰 검사용 플러그인 두 개를 번들한 커스텀 빌드를 써요. 인증을 각 서비스가 따로 하지 않고 게이트웨이에서 한 번에 처리하려는 구성이라, Ingress에 인증 플러그인을 붙이면 그 경로로 들어온 요청은 Keycloak 검증을 거쳐야 서비스에 닿아요.

캐시는 서비스군마다 전용 Redis를 뒀어요(Bitnami 차트, Redis 7.4). 하나를 공유하면 관리는 편하지만 한 서비스군의 캐시 폭주가 전체로 번지니까, 처음부터 서비스군별 캐시로 나눴어요. 성격이 다른 한 곳은 자체 Redis와 커넥션 풀러를 따로 두고요.

배치 작업도 요청 경로와 떼어놨어요. 서비스군마다 배치 잡이 하나씩 각자 스케줄로 도는데, 이게 나중에 dev 컷오버에서 중요해져요. 같은 배치가 EKS와 OKE 양쪽에서 동시에 돌면 쿠폰이 두 번 발급되거든요. 여기까지가 실물이고 이 실물을 무엇으로 정의하고 무엇으로 채울지가 아래 결정 네 개예요.

스택은 여섯 갈래로 나눴어요

코드를 어떻게 나눌지가 첫 결정이었어요. Terraform은 자기가 만든 자원 목록을 state라는 파일에 적어 두는데, 이게 하나로 뭉치면 문제가 돼요. 전부 한 스택에 넣으면 작은 변경 하나에도 전체 자원이 plan에 걸리고 실수 하나의 피해 범위도 전체가 되니까요.

그래서 platform 하나에 데이터베이스·Keycloak·SaaS·채용·부트캠프 다섯을 얹는 여섯 갈래로 나눴어요. 이 다섯은 앞의 서비스군 다섯과 다른 묶음이에요. 공용 자원인 데이터베이스와 Keycloak이 각자 스택을 갖고, 서비스군 중 셋이 자기 스택을 가져요. 아래쪽 platform이 VCN·OKE·Vault·IAM을 만들고, 위쪽 다섯이 remote state로 그 결과를 참조해요.

대신 스택을 나눈 만큼 스택 사이 의존이 생겨요. 위쪽 다섯은 아래쪽 platform의 출력에 묶여 있죠. 그래도 이 선택은 나중에 값을 했어요. prod에서 스택 하나의 변수 파일이 어긋났을 때 피해 범위가 그 스택에 갇혔거든요.

진실은 클러스터 밖에 뒀어요

두 번째 결정은 “클러스터의 현재 상태를 어디서 읽을 것인가”였어요. 콘솔이 유일한 문서였던 EKS를 겪은 뒤라, 클러스터에 직접 넣어야만 아는 값은 만들지 않기로 했어요.

비밀값은 클러스터에 직접 넣지 않고 OCI Vault에 두고 External Secrets가 가져와 Secret으로 만들어요. 매니페스트는 Git에만 두고 반영은 ArgoCD가 해요. 클러스터 상태를 알고 싶으면 클러스터가 아니라 Git과 Vault를 보면 된다는 게 이 구성의 목적이에요.

sync는 dev·prod 모두 수동으로 뒀어요. 자동 sync가 편하긴 한데, Git에 push하는 순간 운영이 바뀌는 게 이 시점에는 부담이었거든요. 특히 prod는 오래된 리비전이 잘못 반영되면 되돌리기가 어려워요. 그래서 누르기 전에 ArgoCD 화면에서 차이를 보는 절차를 남겼어요.

다만 이 구성에는 빈틈이 있어요. Git에 없는 필드는 ArgoCD가 관리하지 않아서 수동 변경이 그대로 살아남아요. 뒤에 나올 두 번째 장면이 그 이야기예요.

values 두 장으로 환경을 나눴어요

세 번째 결정은 ArgoCD Application 자체를 어떻게 관리할지였어요. 서비스가 60개를 넘어가면 Application 정의를 사람이 손으로 유지할 수 없어요. 그래서 Application 정의를 Helm chart로 만들고 환경 차이는 values 파일로만 두는 구조로 갔어요.

argocd/
├── templates/app/      # Application 정의 66개
├── values-dev.yaml     # develop 브랜치 추적, dev 전용 ingressClass
└── values-prod.yaml    # main 브랜치 추적

Application 하나는 이렇게 생겼어요. 서비스마다 다른 건 이름과 kustomize 경로뿐이고, 브랜치·네임스페이스·sync 정책은 전부 values에서 와요.

환경을 하나 더 만들 때 values 파일 하나만 쓰면 서비스 66개가 통째로 따라오게 했어요. dev와 prod의 차이도 파일 두 장을 비교하면 바로 보여요.

토큰은 스스로 갱신하게 했어요

네 번째 결정은 눈에 잘 안 띄는 쪽이에요. 컨테이너 이미지를 ECR과 OCIR 두 곳에서 받아오는데, 둘 다 인증 토큰이 만료돼요. 만료될 때마다 사람이 갱신하면 잊어버리는 날 배포가 멈추니까 양쪽 다 자동화했어요. 다만 만료 주기가 달라서 방식도 다르게 갔어요.

ECR (AWS)OCIR (OCI)
토큰 만료하루 안쪽으로 짧아요90일이라 길어요
갱신 주체클러스터 안 CronJob이 6시간마다 받아와요Terraform이 80일마다 재발급해요
반영 경로네임스페이스 다섯 곳의 Secret을 직접 고쳐요Vault에 저장하면 External Secrets가 배포해요

ECR 쪽은 CronJob이 aws ecr get-login-password로 받은 값을 쿠버네티스 API로 네임스페이스 다섯 곳의 Secret에 넣어줘요. 처음 도는 경우엔 만들고, 있으면 고치고, 예상 못 한 응답이면 중단하게 했어요. OCIR 쪽은 90일 만료라 CronJob이 어울리지 않아서, Terraform의 시간 기반 회전 리소스로 80일마다 재발급하고 Vault에 넣어요. 만료 열흘 전에 갱신되니 주기가 겹칠 일이 없고요.

이런 것들이 이관에서 눈에 안 띄는 부분이에요. 잘 돌아가면 아무도 모르고 안 되면 그날 배포가 전부 멈춰요.

시간을 잡아먹은 건 결정 목록 밖이었어요

계열로 묶으면 네 갈래예요.

이름 하나로 Ingress가 충돌했어요. 기존 Kong이 이미 kong이라는 Ingress 클래스를 쓰고 있어서, dev Kong을 같은 이름으로 띄우면 두 Kong이 같은 Ingress를 서로 가져가려고 해요. dev는 별도 이름으로 나누고 CRD 설치도 껐어요(기존 Kong이 설치해둔 것을 공유). 클러스터가 갈라져 있어도 Ingress 클래스는 이름 하나로 충돌할 수 있다는 걸 여기서 배웠어요.

state가 백지에서 시작했어요. 그 state 파일은 팀이 같이 쓰려면 원격 저장소에 둬야 해요. OCI Object Storage에는 S3 호환 API가 있어서 Terraform의 S3 backend를 그대로 쓸 수 있는데, 대신 함정 세 개를 실측으로 배웠어요.

  • 업로드 체크섬을 나눠 보내는 방식을 OCI가 받지 못해요. skip_s3_checksum 옵션으로 꺼야 업로드가 성공해요.
  • 잠금 파일을 지원하지 않아요. 두 명이 동시에 apply하는 것을 막을 수 없어서 운영자 한 명 가정으로 갔어요.
  • VCN의 DNS 라벨이 코드와 어긋나면 강제 replace가 떠요. 모르고 apply하면 네트워크를 통째로 다시 만들게 돼요.

앞서 테넌시 구조를 바꾼 대가도 여기서 치렀어요. 스택을 합치면 새 스택의 state는 백지에서 시작해요. 클라우드에는 자원이 멀쩡히 돌아가고 있는데도, 새 스택 입장에서는 자기가 만든 게 하나도 없거든요. 그대로 apply하면 이미 있는 걸 또 만들려다 실패해요. 그래서 등록 스크립트를 만들어 실제 자원의 ID를 조회한 뒤 terraform import로 하나씩 state에 집어넣었어요.

Keycloak 26 헬스체크가 세 겹으로 걸렸어요. 인증 서버는 Keycloak 26을 새로 구축했는데, 증상은 관리 화면 무한 로딩이었고 Kong은 뒤에 붙일 서버를 못 찾는다고 답했어요. pod은 0/1 Running이었고요. 원인이 세 겹이었어요.

  1. Keycloak은 17부터 구버전의 /auth 경로 프리픽스를 기본으로 두지 않아요. 컨테이너 상태를 주기적으로 확인하는 probe의 경로부터 어긋나죠.
  2. 경로를 고치면 또 깨져요. 직접 넣은 httpGet 설정이 Helm chart 기본값의 tcpSocket probe를 대체하지 않고 합쳐지면서, 한 probe에 두 방식이 섞이거든요. 이때 pod은 may not specify more than 1 handler type으로 생성 자체가 안 돼요.
  3. chart가 제공하는 custom probe 설정으로 기본값을 통째로 덮어써야 풀려요.

이 순서를 문서로 남겨뒀고, 나중에 prod를 구축할 때 그대로 재사용됐어요.

업그레이드는 계단으로 밟았어요. CVE 하나가 공개됐는데 쓰던 1.33.1 라인에는 대응 빌드가 없었고, 1.33.10 라인부터 있었어요. 1.33.10으로 넘어가는 김에 최신인 1.35.2까지 가기로 했는데, 쿠버네티스는 마이너 버전을 건너뛰는 업그레이드를 지원하지 않아요. 그래서 1.33.10 → 1.34.2 → 1.35.2, terraform apply 세 번의 계단을 밟았어요. 노드는 한 대씩 교체했어요. 정식 커널 패치가 나오기 전까지는 OCI가 전 노드에 자동 배포하는 완화 DaemonSet이 방어하고 있었어요.

업그레이드 전에 정책 엔진 Kyverno도 손봤어요. Kyverno는 클러스터로 들어오는 요청을 가로채 검사하는데, 업그레이드 중에는 이 연결의 호환이 깨질 수 있거든요. 검사기가 응답하지 못해도 요청을 통과시키도록 정책을 미리 낮췄다가, 업그레이드가 끝난 뒤 복원했어요.

dev를 굴리다 두 장면을 만났어요

같은 dev 클러스터인데 문제를 알려주는 방식은 정반대였던 두 경우가 있어요.

첫 번째 장면에서는 신호가 원인을 곧장 가리켰어요. 6월 23일 dev 노드들이 파드를 퇴거시키기 시작했어요. 쿠버네티스가 붙인 사유는 임시 저장 공간 부족이었어요. 실측해 보니 boot volume이 50GB인데 실제로 쓸 수 있는 용량은 35.5Gi뿐이었고, 남은 여유가 5~8Gi까지 줄어 있었어요. 컨테이너 이미지가 쌓여서 채운 거였죠.

조치는 boot volume을 100GB로 올리는 것이었는데, 그것만으로는 끝이 아니었어요. OKE는 boot volume을 늘려도 root 파일시스템을 자동으로 확장하지 않거든요. 노드 부팅 시 실행되는 초기화 스크립트(cloud-init)에 oci-growfs를 넣되, OKE 자체 초기화보다 먼저 실행해야 kubelet이 늘어난 용량을 인식하고요. 그렇게 고쳐 노드 6대를 롤링 교체한 뒤 35.5Gi는 88.9Gi가 됐고, 디스크 압박 상태는 해제됐고, 퇴거되는 파드는 0이 됐어요.

두 번째 장면에서는 도구가 정상이라고만 답했어요. 배포는 ArgoCD로 해요. Git에 둔 매니페스트를 클러스터에 반영해주는 도구죠. 그런데 dev의 배치 Job 하나가 멈춰 있는데도 ArgoCD 화면은 Synced였어요.

원인은 소유권이었어요. Git 쪽 매니페스트에 suspend 필드가 아예 없으면, ArgoCD는 그 필드를 관리 대상으로 삼지 않아요. 그래서 누군가 화면에서 수동으로 적용한 suspend: true가 계속 살아 있고, 도구는 Git과 클러스터가 같다고 답하죠. 틀린 답은 아니에요. Git이 그 필드에 대해 아무 말도 하지 않으니까요.

조치는 환경별 설정을 겹쳐 얹는 overlay 파일에 suspend를 명시해 소유권부터 확보하는 것으로 정리됐어요.

무엇이 달라졌는지 정리했어요

결정 네 개가 실제로 어떻게 나왔는지 정리하면 이래요.

이름 붙인 설계노린 것실제로 나온 것
스택 여섯 갈래거대한 state 하나를 만들지 않으려고 했어요.이 효과는 dev가 아니라 prod에서 확인했어요. 변수 파일이 어긋난 스택 하나에 피해가 갇혔거든요.
진실은 클러스터 밖에클러스터 대신 Git과 Vault만 보면 되게 하려고 했어요.대체로 그렇게 됐지만, Git에 없는 필드는 클러스터에 그대로 남더라고요.
values 두 장환경 차이를 파일 두 장의 차이로만 두려고 했어요.환경을 늘릴 때 values 파일 하나로 서비스 66개가 따라와요.
토큰 자가 갱신사람이 만료 날짜를 기억하지 않게 하려고 했어요.만료 주기가 달라 ECR은 6시간 CronJob, OCIR은 80일 재발급으로 나뉘었어요.

숫자로 확인된 건 디스크 쪽이에요. 노드당 실사용 임시 저장 공간이 35.5Gi에서 88.9Gi가 됐고, 퇴거되는 파드는 0이 됐어요. 클러스터는 쿠버네티스 1.33.1에서 1.35.2까지 apply 세 번으로 올라갔고, 워커 노드는 3대에서 6대가 됐어요.

나머지는 아직 못 쟀어요. EKS와 OKE의 비용 차이도, 배포 한 번에 걸리는 시간도 재보지 않았어요. 예산은 월 $1,000에 알림만 걸어둔 상태고 실제 청구액을 EKS 시절과 나란히 놓고 본 적은 없어요.

dev를 넘기고 prod로 갔어요

6월 19일, dev의 배치 스케줄이 EKS에서 OKE로 넘어갔어요. 같은 스케줄이 양쪽에서 돌면 쿠폰이 중복 발급되니까, OKE 쪽 가동을 확인한 뒤 EKS 쪽을 정지하는 순서였고요. 이것으로 dev는 사실상 OKE가 기준 환경이 됐어요.

원래는 여기서 이어서 prod까지 제가 할 계획이었어요. 그런데 채용 시스템 구축 같은 급한 일이 겹치면서 손을 뗐고 prod는 다른 분이 맡게 됐죠. 그러다 6월 말에 그 일이 저한테 다시 왔어요. 2편에서는 돌아가는 인프라를 파악하는 것부터, 그대로 apply했으면 클러스터가 통째로 교체될 뻔했던 설정 차이를 잡아낸 일, 그리고 컷오버 주간에 몰린 문제들까지 이어서 써요.
