Slack 배포 알림이 invalid_blocks로 거절됐는데 GitHub Actions는 성공이었어요

2026년 11월 27일13 min read

운영 배포를 마치면 봇이 배포 알림 채널에 올린 메시지에 완료 이모지를 달아요. 여러 앱을 연달아 배포한 날, 어드민 앱의 배포 알림만 채널에 오지 않았어요. 어드민 배포 워크플로는 성공으로 끝나 있었어요. 알림 스텝 로그 마지막에는 이 한 줄이 있었어요.

알림이 실패했는데 워크플로는 왜 성공이었는지, 메시지의 어느 부분이 거절됐는지를 찾아야 했어요.

이 알림은 Slack 메시지를 블록(머리글, 본문 칸 같은 조각) 여러 개로 짜서 보내요. 이번엔 변경 내역을 담은 본문 블록이 Slack 한도 3,000자를 넘어 메시지 전체가 거절됐어요. 알림 스텝은 실패를 감지하고도 오류 코드를 출력만 해서, 워크플로는 성공으로 보였어요. 변경 내역은 줄 단위로 한도 안에서 잘랐고, 알림이 실패하면 잡은 성공으로 둔 채 그 스텝만 실패하게 바꿨어요.

실패를 출력하고도 성공한 스텝

원인은 스텝 스크립트 마지막 줄의 응답 확인이었어요. 이 스텝은 Slack Web API의 chat.postMessage(봇이 채널에 메시지를 올리는 API)를 curl로 부르고, 응답을 이 한 줄로 확인해요.

Slack Web API 응답에는 성공 여부를 알리는 ok 값이 늘 들어 있어요. 실패하면 error에 오류 코드가 들어요. 셸에서 A && B || C는 (A && B) || C로 묶여요.

  • 실패 응답: 대괄호 검사가 참이라 echo가 오류 코드를 출력해요. echo가 0으로 끝나서 || true까지 가지도 않아요.
  • 성공 응답: 대괄호 검사가 거짓이라 echo를 건너뛰어요. 이때 || true가 없으면 이 줄이 1로 끝나서, 정상 전송인데 스텝이 실패해요.

어느 쪽이든 스텝은 종료 코드 0으로 끝났어요. 실패 경로에는 스텝을 실패시키는 명령이 처음부터 없었어요.

한도를 넘은 블록 하나

메시지를 다시 만들어 재 보니 변경 내역 블록 하나만 한도를 넘었어요. 로그에는 응답의 error 값만 남아 있어서, 어느 블록이 왜 틀렸는지는 알 수 없었어요. 배포 당시에도 변경 내역이 길어서 넘친 것으로 짐작만 했고 확인하지는 못했어요. 그래서 그 실행의 로그에 찍힌 변경 내역 48줄을 워크플로의 jq 프로그램에 넣어 메시지 JSON을 만들고, 블록마다 text 길이를 쟀어요.

배포변경 내역 블록
알림이 빠진 배포48줄, 3,017자
그 전 운영 배포 5건416줄, 194767자

나머지 블록은 머리글과 컨테이너 이미지 주소처럼 길이가 거의 정해진 값이라 모두 200자가 안 됐어요. 그 전 5건의 로그에는 알림 실패 출력이 없었어요.

변경 내역 블록은 본문 칸인 section 블록이에요. Slack 문서에 적힌 section 블록 text의 최대 길이는 3,000자예요. 이 블록에는 배포에 들어간 PR과 커밋의 제목이 한 줄씩 들어가요. Slack 오류 표에는 블록이 너무 길 때 쓰는 msg_blocks_too_long도 따로 있어서, invalid_blocks라는 이름만으로는 길이 문제라고 판단하기 어려워요.

줄 단위로 자른 변경 내역

변경 내역은 한도 안까지만 줄 단위로 싣고, 못 실은 줄 수와 릴리즈 노트 링크를 마지막 줄에 붙였어요. 메시지를 만드는 jq 프로그램은 별도 파일로 옮겼어요. 워크플로와, 블록 길이를 검사하는 스크립트가 같은 파일을 jq -n -f로 불러요.

  • 상한 2,900자: 한도 3,000자에서 100자를 남겼어요. jq의 length는 문자열을 유니코드 코드 포인트(글자마다 붙은 번호) 단위로 세서 📦 같은 이모지를 1자로 세요. Slack이 이모지를 몇 자로 세는지는 문서에서 찾지 못했어요.
  • 안내 줄 예산: 변경 내역에 쓸 수 있는 글자 수(예산)는 상한에서 제목, 안내 줄 길이, 줄바꿈 2자를 뺀 값이에요. 안내 줄 길이는 못 실은 줄이 세 자리 수일 때의 「… 외 999건은 … 에서 보기」로 잡아서, 안내 줄을 붙인 뒤에도 상한을 넘지 않아요.
  • 줄 단위 판정: 줄을 통째로 싣거나 빼서, PR 제목이 중간에서 끊기지 않아요. 한 줄이라도 예산을 넘으면 그 뒤 줄은 모두 빼고 건수만 세요.
  • 안내 줄 링크: 못 실은 줄은 릴리즈 노트 링크(릴리즈를 못 찾으면 PR이나 커밋 링크)로 이어 보게 해요.

같은 48줄을 넣으면 옛 프로그램은 변경 내역 블록을 3,017자로 만들고, 새 프로그램은 2,816자로 만들어요. 새 쪽은 마지막 3줄 대신 「외 3건」 안내가 붙어요. 검사 스크립트는 Slack에 보내지 않고, 짧은 내역과 긴 내역과 빈 내역으로 만든 메시지 JSON이 한도 안인지 jq로 확인해요.

스텝만 실패로 남긴 알림

알림이 실패하면 알림 스텝만 실패로 끝내고, 잡은 성공으로 남겼어요. continue-on-error: true는 스텝이 실패해도 잡을 실패로 치지 않게 하는 옵션이에요.

같은 잡 뒤쪽에는 if: failure()로 도는 빌드 실패 알림 스텝이 있어요. exit 1만 넣을 때와 비교하면 차이는 이래요.

실패 처리잡 결과빌드 실패 알림
exit 1만실패나감
continue-on-error + exit 1성공안 나감
  • 잡 결과: 이 스텝이 돌 때 이미지 푸시와 배포 저장소의 이미지 태그 갱신이 이미 끝나 있어요. 잡이 실패로 바뀌면 그 작업까지 실패한 것처럼 보여요.
  • 빌드 실패 알림: failure()는 앞선 스텝이 하나라도 실패하면 참이 돼요. GitHub 문서에 따르면 continue-on-error를 붙인 스텝은 실패해도 최종 결과(conclusion)가 success로 남아요. 그래서 failure()가 참이 되지 않는다고 보고 이렇게 짰어요.

실패는 대신 실행 화면에 남아요.

  • 오류 annotation: echo "::error title=…::…" 형식의 워크플로 명령으로 실행 요약에 오류 표시를 남겨요. 알림만 손으로 올려 달라는 안내를 같이 적어요.
  • 스텝 요약: $GITHUB_STEP_SUMMARY 파일에 오류 코드를 덧붙여 써요.

채널로 따로 알리는 장치는 넣지 않았어요. 이번처럼 알림이 안 와서 실행을 열어 보면, 거기에 오류 표시가 남아 있게 했어요.

고친 분기는 이렇게 확인했어요.

  • 실패 분기 시험: 새 셸 분기만 떼어 가짜 응답 4가지를 넣었어요. ok: false 응답, 빈 응답, JSON이 아닌 응답은 종료 코드 1과 ::error 출력을 냈어요. ok: true 응답만 0으로 끝났어요.
  • 빈 응답의 오류 코드: 처음엔 .error // "응답 없음"으로 기본값을 줬는데, 빈 응답에서는 오류 코드가 빈칸으로 찍혔어요. 입력이 비면 jq가 아무것도 출력하지 않아서 기본값이 붙을 자리가 없었어요. 그래서 셸 쪽 ${ERR:-응답 없음}으로 기본값을 옮겼어요.

고친 뒤 그날 어드민을 한 번 더 배포했고, 그 알림은 채널에 도착했어요. 그 배포의 변경 내역은 한도의 절반이 안 돼서 줄을 자를 일이 없었어요. 줄을 자른 알림도, 고친 실패 분기도 아직 Actions에서 실제로 돈 적은 없어요.

Slack으로 배포 알림을 보내는 워크플로라면 이런 곳을 확인해 보면 좋아요.

  • 길이 상한: 사람이 쓴 글이 들어가는 블록에 상한이 있는지 봐요.
  • 실패 시 종료 코드: 응답의 ok가 false일 때 스텝이 실제로 0이 아닌 코드로 끝나는지 봐요.
  • 복사본: 같은 알림 코드를 복사해 쓴 다른 워크플로가 있는지 봐요.

만든 메시지 JSON의 블록별 길이는 이 한 줄로 볼 수 있어요. context 블록(작은 보조 글씨 블록)은 글이 elements 안에 있어서 0으로 나와요.
