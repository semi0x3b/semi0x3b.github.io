OpenAI API 키를 잠그며 알게 된 것: IP 허용 목록, 모델 제한, 키 분리

OpenAI API 키를 잠그며 알게 된 것: IP 허용 목록, 모델 제한, 키 분리

2026년 10월 15일19 min read

OpenAI 사용 기록(Logs)에 서비스 코드가 쓰지 않는 모델 이름이 찍혀 있었어요.

Input     Output                          Model
hi        Hi! How can I help you today?   gpt-6-astra
…
say OK    OK                              gpt-5.5-2026-04-23
…

Logs 목록 화면에는 어느 키와 어느 주소에서 온 호출인지 나오지 않아서 출처를 가릴 수 없었어요. 키 유출이 의심되는 정황은 따로 있었고, 키를 바꾸면서 OpenAI 쪽 설정을 다시 봤어요. IP 허용 목록은 만들어져 있었지만 화면상 어느 범위에도 적용되지 않은 상태였어요. 모델 제한은 아예 없었어요.

  • OpenAI IP 허용 목록은 적용 범위(Coverage)를 지정해야 조직이나 프로젝트에 붙어요. 화면에 Not covered로 나오면 어디에도 붙지 않은 상태예요.
  • 모델 제한은 키가 아니라 프로젝트에 걸려요. 프로젝트는 조직 안에서 키를 묶는 단위예요. 한 프로젝트에 여러 서비스의 키가 있으면 모든 서비스가 쓰는 모델을 합쳐 허용 모델 목록에 넣어요.
  • 서비스가 쓰는 키로 호출해 보니 허용하지 않은 모델은 403으로 막혔어요. 그 과정에서 이미 폐기된 모델을 부르던 기능도 찾았어요.

키는 쿠버네티스 위의 서비스에 이렇게 들어가요.

OCI Vault(비밀 저장소) ─ ESO가 복사 → 쿠버네티스 Secret ─ 파드가 시작할 때 읽음 → 환경변수

External Secrets Operator(ESO)는 외부 비밀 저장소의 값을 쿠버네티스 Secret으로 옮겨 주는 도구예요. 일부 서비스는 AWS Secrets Manager에서 키를 직접 읽어요.

유출을 판단한 근거와 경로는 이 글에서 다루지 않아요.

잠그는 장치는 걸리는 단위가 서로 달라요

IP 허용 목록, 모델 제한, 키 분리는 걸리는 단위가 서로 달라요. IP 허용 목록과 모델 제한은 새어 나간 키로 할 수 있는 일을 줄여요. 키 분리는 키가 샜을 때 바꿀 범위를 줄여요.

OpenAI 계정은 조직 안에 프로젝트를 여러 개 둘 수 있어요. API 키는 프로젝트 안에서 발급해요.

조직 ─ IP 허용 목록 (Coverage로 조직이나 프로젝트를 지정)
 └ 프로젝트 ─ 모델 제한
     ├ 키 (서비스 A)
     └ 키 (서비스 B)
장치걸리는 단위설정 위치효과
IP 허용 목록조직 또는 프로젝트조직 설정의 IP allowlists목록 밖 주소의 호출을 막아요
모델 제한프로젝트프로젝트 설정의 Limits(Model usage)허용하지 않은 모델 호출을 막아요
키 분리키API keys한 키가 새도 그 키를 쓰는 곳만 바꿔요

IP 허용 목록과 모델 제한은 키마다 따로 걸 수 없어요. 한 프로젝트의 키를 쓰는 서비스를 전부 알아야 허용할 주소와 모델을 채울 수 있어서, 키가 쓰이는 곳부터 찾았어요.

키가 쓰이는 곳부터 찾아요

옛 키 하나가 여러 비밀 저장소와 서비스에 퍼져 있었어요.

  • 쓰는 서비스: 4개
  • 들어 있는 비밀 저장소: 6곳(OCI Vault 4곳, AWS Secrets Manager 2곳)
  • 같은 값을 담은 환경변수: 한 파드 안에 이름이 다른 3개

파드 안에서는 키가 옛 키로 끝나는지만 비교하고 결과만 출력했어요.

파일을 grep -r로 뒤질 때는 -l로 파일 이름만 받아요. 그냥 찾으면 일치한 줄이 통째로 출력돼서 키 원문이 화면에 찍혀요. 조사 중에 한 번 실제로 그렇게 찍혔어요.

비밀 저장소 밖에서도 옛 키가 나왔어요. Helm은 배포할 때마다 넣은 설정값(values)을 Secret에 기록해 둬요. Argo CD(배포 도구)는 Application 리소스에 values를 직접 적으면 그 값이 리소스 정의(spec)에 평문으로 남아요.

위치확인 방법
쿠버네티스 Secretkubectl get secret -A -o json을 디코드해 값이 옛 키로 끝나는지 비교해요
Helm 릴리스 기록owner=helm 레이블 Secret의 release 값을 base64 두 번, gzip 한 번 풀어 옛 키의 긴 조각을 찾아요
Argo CD Application speckubectl get applications -A -o json에서 옛 키의 긴 조각을 찾아요

값 하나를 통째로 비교할 때는 끝 4자리로 충분해요. Helm 기록이나 Application JSON처럼 큰 텍스트에서 찾을 때는 끝 4자리가 다른 값과 우연히 일치할 수 있어서, 끝 12자리처럼 긴 조각을 써요.

ESO가 만든 Secret은 저장소의 새 값으로 다시 채워져요. Argo CD values로 만든 Secret은 ESO가 관리하지 않아서 values를 고치기 전까지 바뀌지 않아요. Helm 기록과 Argo CD spec에 남은 옛 키도 그대로예요. 이런 곳은 OpenAI에서 옛 키를 폐기해야 쓸모가 없어져요.

허용할 IP는 파드 안에서 잰 주소예요

허용할 주소는 서비스의 요청이 인터넷으로 나갈 때 찍히는 주소(출구 주소)예요. 클라우드 콘솔에서 짐작하지 않고 키를 쓰는 서비스 파드 안에서 직접 쟀어요.

같은 클러스터의 파드는 모두 NAT 게이트웨이 주소 하나로 나갔어요. NAT 게이트웨이는 사설망 안의 요청을 공인 주소 하나로 모아 내보내는 장치예요. 개발과 운영 클러스터는 NAT가 달라서 출구 주소도 클러스터마다 하나씩이었어요. 쿠버네티스 밖에서 키를 읽는 배포(VM 등)가 있으면 그 출구 주소도 따로 재요.

사무실 회선 주소는 기존 목록에 들어 있어서, 사무실에서 부르면 목록이 붙어 있든 아니든 똑같이 통과해요. 그래서 막히는지는 목록 밖 회선에서 봐야 해요.

Coverage가 Not covered면 목록이 어디에도 붙지 않아요

적용 범위를 지정하지 않은 허용 목록은 조직에도 프로젝트에도 붙어 있지 않아요. 화면에는 이렇게 나와 있었어요.

Name           IP ranges         Coverage
ipallow_...    (허용 주소 목록)   Not covered

화면 안내문에는 조직 단위와 프로젝트 단위의 관계가 이렇게 적혀 있어요.

Project-level coverage overrides organization-level coverage.

조직과 프로젝트에 목록이 둘 다 붙어 있으면 그 프로젝트의 호출에는 프로젝트에 붙인 목록이 적용된다는 뜻이에요. 저는 서비스 키가 있는 프로젝트를 적용 범위로 지정했어요.

  • 지정 순서: 목록을 다 채운 뒤 적용 범위를 지정해요. 순서를 바꾸면 출구 주소가 아직 목록에 없는 서비스의 호출이 막혀요. 안내문 기준으로 반영까지 최대 15분이 걸려요.
  • 남은 확인: 목록 밖 회선에서 실제로 막히는지는 아직 확인하지 못했어요. 휴대폰 핫스팟처럼 목록에 없는 회선에서 호출해 볼 차례예요.

모델 제한은 프로젝트에 하나만 걸려요

허용하지 않은 모델을 부르면 이렇게 거부되는데, 메시지에 키가 아니라 프로젝트가 나와요.

403 model_not_found
Project `proj_...` does not have access to model `gpt-6-astra`

서비스마다 다른 키로 불러도 메시지의 프로젝트는 같았어요. 그래서 허용 모델 목록 하나가 그 프로젝트의 모든 서비스에 똑같이 걸렸어요. 한 서비스만 쓰는 모델을 빠뜨리면 그 서비스가 막혀요.

옛 키도 같은 프로젝트에 있어서 gpt-6-astra를 옛 키로 부르면 같은 403이 났어요. 옛 키를 폐기하기 전에도 모델 제한은 옛 키에 걸려 있어요.

허용할 모델은 코드와 설정에서 모아요

허용할 모델은 각 서비스의 코드와 설정에 적힌 모델 이름을 합친 목록이에요. 기본 브랜치에서 모델 이름 문자열을 모았어요.

코드만 보면 놓치는 게 있었어요.

  • 설정으로 바꾸는 모델: 환경변수로 모델 이름을 받는 서비스는 코드에 기본값만 있어요. 파드 환경변수의 모델 값도 확인해요.
  • 선택 목록에 없는 이름: 코드에 있던 gpt-5.2-chat-latest는 Model usage 목록에서 고를 수 없었어요. 이미 폐기된 모델이라 검증 호출에서 404가 났어요.

응답 코드와 메시지로 허용, 제한, 폐기를 가려요

200은 허용, 403은 모델 제한, 404 has been deprecated는 모델 폐기예요. 설정을 저장한 뒤 서비스 파드 안에서 그 서비스의 키로 짧은 호출을 보내 확인했어요. 키를 파드 밖으로 꺼내지 않으려고 파드 안에서 실행했어요.

OPENAI_API_KEY는 그 서비스가 키를 담는 환경변수 이름으로 바꿔요.

응답뜻본 모델
200허용됨코드에서 쓰는 모델
403 does not have access to model모델 제한에 걸림gpt-6-astra, gpt-6-sol, gpt-5.5
404 has been deprecated모델 자체가 폐기됨gpt-5-chat-latest, gpt-5.1-chat-latest, gpt-5.2-chat-latest

폐기된 모델은 모델 제한과 상관없어요. 이 모델들은 어느 키로 불러도 404가 났어요. 메시지는 부르는 API마다 달랐어요.

  • Chat Completions API(/v1/chat/completions, 위 스크립트): 404 has been deprecated
  • Responses API(/v1/responses): 404 does not exist or you do not have access to it

Responses API의 메시지에 access가 들어 있어도 403 모델 제한이 아니라 폐기예요.

gpt-5.1-chat-latest를 쓰던 기능은 이미 실패하고 있었어요. 한 서비스가 Responses API로 이 모델을 불러서 운영 로그에 같은 오류가 남아 있었어요. 오류는 모델 제한을 걸기 전 날짜부터 찍혀 있어서 이번 제한 때문에 생긴 실패가 아니었어요. 고치려면 코드의 모델 이름을 바꿔야 해요.

공용 키는 목적에 맞게 나눠요

여러 서비스가 같이 쓰던 공용 키를 목적에 맞게 나눠 새로 발급했어요. 키 하나를 여러 곳이 같이 쓰면 교체할 때마다 그 곳을 전부 건드려야 해요.

공용 키목적별 키
한 키가 새면 고칠 비밀 저장소6곳그 키를 쓰는 곳만
재시작할 서비스4개그 키를 쓰는 서비스만

키를 나눠도 같은 프로젝트에 있으면 모델 제한과 IP 허용 목록은 똑같이 걸려요. 키마다 막는 범위를 다르게 하려면 프로젝트를 나눠야 해요.

키를 바꿔도 새 키가 닿지 않는 곳이 있어요

저장소 값을 바꿔도 새 키가 닿지 않는 곳이 있었어요. 가장 놓치기 쉬운 건 재시작하지 않은 파드였어요.

  • 재시작하지 않은 파드: 환경변수는 컨테이너가 시작할 때 한 번 읽어요. 교체 전에 시작한 파드는 Secret이 새 키로 바뀐 뒤에도 환경변수에 옛 키가 그대로 남아 있었어요.

  • 비어 버린 키: 같은 값을 담던 환경변수 3개 중 1개가 교체 과정에서 빈 값이 됐어요. 그 환경변수를 읽는 클라이언트를 파드 안에서 만들어 호출해 보니 이렇게 실패했어요.

    401 Missing bearer authentication in header

    OpenAI 파이썬 클라이언트는 빈 문자열을 키로 받아도 클라이언트를 만들 때는 오류를 내지 않아요. 실패는 첫 호출에서야 나와요.

  • 이미지 안의 .env: 다른 서비스의 이미지에서 OpenAI 키가 든 .env 파일이 나왔어요. 빌드할 때 복사된 파일이라 Secret을 바꿔도 이 값은 그대로예요. .env를 빌드에서 빼고 키는 Secret으로 받게 옮겨요.

옛 키는 맨 마지막에 폐기해요. 먼저 폐기하면 재시작하지 않은 파드가 401로 실패해요. 폐기 전에는 허용 모델을 옛 키로 불러도 200이 나와서, 옛 키가 막혔는지는 폐기한 뒤 401이 나는지로 확인해요. 한 서비스만 쓰던 키는 새 키로 200이 나는 걸 확인하고 폐기했어요. 폐기한 키로 불러 보니 401이 났어요.

적용한 뒤 이렇게 확인해요

  • IP 허용 목록의 Coverage가 Not covered가 아닌지 화면에서 봐요.
  • 허용한 주소가 파드 안에서 잰 출구 주소와 같은지 curl -s https://api.ipify.org로 봐요. 쿠버네티스 밖 배포의 출구 주소도 같이 봐요.
  • 목록 밖 회선(휴대폰 핫스팟 등)에서 호출해 거부되는지 봐요. 사무실 회선이 목록에 있으면 사무실에서는 확인이 안 돼요.
  • 허용 모델이 코드의 모델 이름과 파드 환경변수의 모델 값을 모두 포함하는지 git grep 결과와 대조해요.
  • 서비스마다 자기 키로 허용 모델은 200, 막을 모델은 403이 나는지 파드 안에서 호출해 봐요.
  • 404가 나는 모델이 코드에 남아 있지 않은지 같은 호출로 봐요. 메시지는 API마다 달라요.
  • 키를 바꾼 뒤 모든 파드를 재시작하고, 파드 환경변수가 새 키로 끝나는지 봐요.
  • 키 환경변수 중 빈 값이 없는지 같은 대조에서 봐요.
  • 컨테이너 안에 키가 든 .env가 없는지 ls -a로 작업 디렉토리를 봐요.
  • 옛 키를 폐기한 뒤 옛 키 호출이 401로 바뀌는지 봐요.
  • Logs에 코드에 없는 모델 호출이 더 찍히지 않는지 봐요.
