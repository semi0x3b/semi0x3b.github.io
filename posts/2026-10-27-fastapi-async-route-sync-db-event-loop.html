느린 요청 하나에 FastAPI 헬스체크까지 멈춰서 파드가 재시작됐어요

느린 요청 하나에 FastAPI 헬스체크까지 멈춰서 파드가 재시작됐어요

2026년 10월 27일13 min read

Warning  Unhealthy  Liveness probe failed: Get "http://(파드 IP)/health": context deadline exceeded (Client.Timeout exceeded while awaiting headers)
Normal   Killing    Container (컨테이너명) failed liveness probe, will be restarted

배포 전에 dev 파드 안에서 읽기 요청 몇 개를 순서대로 보내던 중이었어요. 그중 하나는 필터 없이 부르면 전체 목록을 내려주는 공개 API였어요. 이 요청의 응답이 오지 않는 동안 쿠버네티스가 주기적으로 부르는 /health도 같이 답하지 않았고, 잠시 뒤 파드가 위 이벤트를 남기고 재시작됐어요. 목록 요청이 느린 건 그렇다 쳐도, 아무 일도 하지 않는 /health는 왜 같이 멈췄을까요?

원인은 async def 라우트 안에서 바로 부른 동기 함수였어요. FastAPI는 async def 라우트를 이벤트 루프에서 돌리는데, 이벤트 루프는 스레드 하나로 요청 여러 개를 번갈아 처리하다가 동기 함수를 만나면 그 함수가 끝날 때까지 다른 요청으로 넘어가지 못해요. 그래서 같은 패턴의 공개 라우트 29개에서 그 호출만 이벤트 루프 밖의 작업용 스레드(스레드풀)로 옮겼고, 느린 DB를 흉내 낸 재현에서 /health 최대 지연이 21,231ms에서 33ms로 줄었어요.

파드가 재시작되기까지

liveness probe는 쿠버네티스가 컨테이너가 살아 있는지 주기적으로 묻는 요청이에요. 이 서비스는 /health를 10초마다 부르고, 5초 안에 답이 없으면 실패로 세고, 3번 연속 실패하면 컨테이너를 재시작해요. 그러니 /health가 30초 가까이 답을 못 하면 컨테이너는 재시작돼요.

순서일어난 일
목록 요청 직후그 요청은 응답이 없었고, 같은 파드의 /health도 응답하지 않았어요.
설정상 약 30초 뒤liveness probe가 3번 연속 실패해 쿠버네티스가 컨테이너 재시작을 결정했어요.
재시작 뒤종료된 컨테이너의 마지막 요청 로그가 그 목록 경로였어요. 그날 밤 같은 확인 요청에 재시작이 모두 2번 있었어요.

의심한 것과 원인

의심한 것은 3개였어요. 앞의 2개는 멈춤을 길게 만든 조건이었고, 루프를 막은 건 마지막이었어요.

  • 목록 요청이 느리다: 사실이지만 느린 것만으로는 /health가 멈추지 않아요. dev와 같은 규모의 데이터를 로컬에 넣고 보내니 응답 하나를 만드는 데 19초가 걸렸어요. 항목마다 같은 객체 변환을 반복하던 코드라 변환을 한 번만 하게 고쳤고, 로컬 계산 시간은 0.3초대로 내려왔어요.
  • dev 파드의 CPU가 적다: 이것만으로는 설명이 안 돼요. dev 파드는 CPU 0.5코어라 같은 계산이 더 오래 걸려요. 하지만 CPU에 여유가 있는 로컬 재현에서도 목록을 계산하는 동안 /health는 똑같이 답하지 않았어요.
  • async def 안에서 동기 함수를 부른다: 이게 원인이에요. /health는 async def로 dict 하나를 돌려주는 라우트예요. 느린 목록 라우트도 async def인데, 그 안에서 SQLAlchemy 조회와 응답 변환을 하는 동기 함수를 await 없이 바로 불렀어요. 19초짜리 변환도 이 동기 함수 안에서 돌았어요.

asyncio 이벤트 루프는 스레드 하나에서 요청 여러 개를 번갈아 처리해요. 번갈아 처리한다고 해도 아무 때나 바꾸는 게 아니라, 처리 중인 요청이 await로 기다리는 중이라고 알릴 때만 다른 요청으로 넘어가요. 동기 함수에는 await 지점이 없으니, 그 함수가 끝날 때까지 루프는 다른 요청을 처리하지 못해요. 그 사이에 들어온 /health 요청은 연결은 맺어지지만 핸들러가 실행될 차례를 받지 못해요. 첫머리 이벤트의 awaiting headers가 그 상태예요.

FastAPI는 라우트를 def로 선언하면 알아서 스레드풀에서 돌려 주지만, async def로 선언하면 루프에서 그대로 실행해요. 이 서비스의 공개 라우트는 대부분 async def였고, 그 안에서 동기 함수를 바로 부르는 라우트가 많았어요. 요청이 빠를 때는 티가 나지 않다가 느린 요청 하나가 들어오면 /health까지 같이 멈추는 구조였어요.

호출 한 줄만 스레드풀로 옮기기

응답이 바뀌면 안 되니, 라우트 안에서 응답을 만드는 동기 함수 호출 한 줄만 run_in_threadpool로 넘겼어요. run_in_threadpool은 동기 함수를 이벤트 루프 바깥의 작업용 스레드 묶음(스레드풀)에서 돌리고, 라우트는 그 결과를 await로 기다려요. 루프는 await에서 다른 요청으로 넘어가니까, 조회가 도는 동안에도 /health가 답할 수 있어요.

더 쉬운 길은 async def를 def로 바꿔 FastAPI가 라우트 전체를 스레드풀에서 돌리게 하는 거예요. 그런데 이 라우트 중 8개는 fastapi-cache2 0.1.9의 @cache로 감싸여 있어요. 이 데코레이터는 캐시에 값이 없으면 라우트 함수를 await func(...)로 불러서, 라우트가 def이면 첫 요청부터 깨져요. 그래서 8개는 def로 못 바꿨고, 나머지 21개도 같은 방식으로 맞췄어요.

같은 패턴이 어디까지인지는 앱의 라우트 테이블을 돌며 셌어요. 라우트 함수마다 inspect.iscoroutinefunction으로 async def인지 보고, 소스에 get_response( 같은 동기 호출 패턴이 있는지 정규식으로 걸렀어요. 공개 라우트에서 31개가 나왔고, 그중 2개는 따로 결정할 일이 남아 있어 이번에는 뺐어요. 나머지 29개는 함수마다 호출이 정확히 한 곳인지 확인하면서 바꾸는 스크립트로 일괄 적용했어요.

고친 뒤 확인한 것과 남은 것

  • 스레드에서 도는지: 고친 라우트마다 응답을 만드는 함수를 가짜로 바꿔 넣는 회귀 테스트를 뒀어요. 가짜 함수는 asyncio.get_running_loop()를 불러서, RuntimeError가 나면 루프 밖 스레드이고 아니면 루프 위라 실패예요.
  • 응답이 그대로인지: 고치기 전 서버와 고친 서버를 나란히 띄우고 같은 1,201개 요청을 보냈어요. 정상 입력과 잘못된 입력을 섞었고, 상태 코드와 헤더와 본문 모두 차이가 0이었어요. 서버가 다른 서비스로 보내는 요청도 같았어요.
  • 느린 DB에서도 /health가 바로 답하는지: DB 앞에 중계 서버(TCP 프록시)를 두고, DB에서 앱으로 오는 패킷마다 150ms씩 늦췄어요. 공개 라우트 5개에 요청 14개를 동시에 보내면서 /health를 계속 불러 지연을 쟀어요. 캐시를 피하려고 id는 바꿔 가며 보냈어요. 14개 중 1개는 앞서 제외한 라우트로 가는 요청이라 고친 뒤에도 루프에서 돌았어요.

문제의 목록 라우트는 이 29개보다 먼저, 변환 반복을 줄이는 수정과 함께 run_in_threadpool로 고쳐 dev에 올렸어요. 같은 요청을 한 번 더 보내니 7MB 응답을 내려주는 데 7.79초가 걸렸어요. 로컬 0.3초대와의 차이는 나눠서 재지 않았지만, 그 요청 동안 liveness probe 실패 이벤트는 없었고 파드도 재시작되지 않았어요.

14개 요청이 끝나는 시간이 함께 줄어든 건 조회가 병렬로 돌았기 때문으로 보여요. 이 서비스는 DB 연결을 재사용하는 커넥션 풀 없이(NullPool) 세션을 열 때마다 새 연결을 열어요. 전에는 조회가 루프 위에서 하나씩 돌았고, 이제는 스레드풀 한도만큼 동시에 돌아요. 그래서 아직 끝나지 않은 확인이 있어요.

  • 운영 DB 연결 상한을 넘지 않는지: 아직 대조하지 않았어요. 스레드풀 기본 한도는 프로세스당 40이라 DB 연결도 그만큼 동시에 열릴 수 있어요. 이 수정은 운영에도 나갔는데, 같은 구조라면 배포 전에 대조해 두는 편이 안전해요.
  • 다른 경로에도 같은 패턴이 있는지: 있어요. 제외한 라우트와 로그인 사용자용 경로와 관리자 경로에 그대로 남아 있어요.

비슷한 구조라면 async def 라우트 안에서 await 없이 부르는 DB 조회나 HTTP 호출부터 세어 보는 게 좋아요. 이 문제는 평소에는 보이지 않다가 느린 요청이 들어온 뒤에야 “파드가 재시작됐다”로 보여서, 원인이 요청 쪽에 있다는 걸 알기 어려워요.
