코드 탐색 에이전트에 코드 그래프를 붙여 봤는데, 셋 다 뺐어요

코드 탐색 에이전트에 코드 그래프를 붙여 봤는데, 셋 다 뺐어요

2026년 9월 03일10 min read

앞 글에서 소개한 봇 얘기 이어서요. 사내 코드베이스를 한글로 물으면 근거 파일과 줄을 인용해 답하는 슬랙 봇인데, 탐색 에이전트가 파일 읽기랑 문자열 검색만 들고 레포를 뒤져요. 함수 호출이나 임포트 관계를 아는 코드 그래프를 붙이면 근거를 더 잘 찾지 않을까 싶어서 도구 세 개를 시험했어요. graphify와 Serena는 같은 질문 4개로 켜고 끄고 8번씩 돌렸고, CodeGraph는 따로 봤어요. 결과부터 말하면 앞의 둘은 핵심 근거 적중이 그대로인 채 응답만 30초에서 60초 느려졌고, CodeGraph는 오히려 정답 요소가 줄었어요. 셋 다 뺐어요.

왜 붙여 보고 싶었냐면

탐색 에이전트한테 준 도구는 파일 읽기, 문자열 검색, 파일 찾기 세 개뿐이에요. 그래서 “이 함수 누가 부르지?”를 알려면 이름을 검색해서 나온 파일을 하나씩 열어 봐야 하고, 이름이 흔하면 그마저 결과에 파묻혀요. 마침 코드베이스를 지식 그래프로 바꿔 준다는 도구 소개 글이 여럿 보였어요. 함수, 클래스, 호출, 임포트 관계를 미리 뽑아 두면 “누가 부르나”를 한 번의 조회로 답한다는 얘기였고요. 안 해 볼 이유가 없었죠.

뭘 어떻게 붙였는지

graphify는 코드를 구문 단위로 읽는 파서(tree-sitter)로 호출·임포트 그래프를 만드는 도구예요. LLM 없이 로컬에서 돌아요. 레포마다 그래프를 만들고 그룹 단위로 합친 다음, 내장된 MCP 서버를 에이전트에 붙였어요. MCP는 에이전트에 도구를 꽂는 표준 방식이라고 보면 돼요.

Serena는 편집기가 쓰는 언어 서버(LSP)로 정의와 참조를 찾아 주는 MCP 서버예요. 파이썬과 타입스크립트 언어 서버를 띄우고, 참조 찾기 쪽 도구만 남기고 나머지는 잠근 채로 붙였어요.

CodeGraph는 심볼 이름과 위치를 인덱싱하는 명령줄 도구예요. 이건 MCP가 아니라, 질문에서 뽑은 식별자로 심볼 위치를 조회한 결과를 프롬프트에 글로 넣어 주는 식이었어요. 그래서 조건이 조금 달라요.

질문은 실제로 들어왔던 것 중에 네 개를 골랐어요. 달력 입력이 특정 기간 안으로만 제한되는지, 시작 후 7일까지만 등록을 받는 유예 규칙이 어디 있는지, 관리자 비밀번호는 어떤 경로로 바꾸는지, 종료된 건은 왜 상태를 못 바꾸는지. 넷 다 프론트, 백엔드, 기획 문서 세 층에 근거가 흩어져 있는 질문이에요. graphify와 Serena는 이 네 질문을 도구를 켠 채로 한 번, 끈 채로 한 번씩 돌려서 도구마다 8번을 비교했고, 프롬프트도 모델도 레포 상태도 같게 뒀어요. CodeGraph는 따로 돌린 실험이라 질문 하나로 정답 요소 세 개가 맞는지를 셌고요. 보는 건 세 가지였어요. 정답 파일을 인용했는지, 몇 초 걸렸는지, 그래프 도구를 실제로 몇 번 불렀는지.

결과

핵심 근거 파일은 graphify든 Serena든 켜든 끄든 8번 다 찾았어요. 시간은 graphify가 켰을 때 평균 126초, 껐을 때 95초였고 Serena는 143초와 82초였어요. 그래프 도구 호출은 둘 다 실행당 1~4번에 그쳤고요. CodeGraph는 켜면 95초, 끄면 80초였는데 시간보다는 정답 요소가 셋 중 둘에서 하나로 줄어든 게 문제였어요.

차이는 부가 근거에서만 났는데, 그마저 방향이 엇갈렸어요. graphify를 켰을 때 더 찾은 건 날짜 입력 컴포넌트 안에서 제한값이 전달되는 경로와 그 검증을 아직 확인하지 않았다고 적힌 기획 문서 한 줄, 그리고 다른 프론트 레포에 있던 드래그 비활성 코드였어요. 반대로 껐을 때 더 찾은 건 정책이 다른 과정에도 적용된다고 확정한 기획 문서, 서버 검증 규칙의 본체, 데이터베이스 제약이었고요. Serena는 켰을 때 기획 문서 근거를 못 찾은 질문이 하나 있었어요. 어느 쪽이 낫다고 하기 애매한 조합이죠.

그런데 실행 사이의 편차를 볼 기회가 우연히 생겼어요. Serena를 처음 붙인 실행에서 에이전트가 도구를 한 번도 안 불렀거든요. 켠 조건인데 사실상 끈 조건을 한 번 더 돌린 셈이 된 거예요. 그 두 실행을 나란히 놓고 보니 같은 조건인데도 부가 근거랑 소요 시간이 켬/끔 차이만큼 흔들리더라고요. 켰을 때 보인 차이는 그 편차 안에 있었어요.

CodeGraph는 코드 심볼만 가리키는 힌트를 주자 탐색이 코드로 쏠려서 기획 문서 레포를 건너뛰는 부작용이 났어요. 그 실험도 되돌렸어요.

도구보다 붙이는 과정에서 배운 게 더 많았어요

제일 컸던 건 에이전트가 도구를 무시하는 문제예요. 그래프 도구를 붙이고 “식별자를 얻으면 문자열 검색보다 먼저 써라”라고 적어 뒀는데, Serena는 여섯 세션 동안 한 번도 안 불렸어요. graphify도 처음 두 실행에서 똑같았고요. 탐색 규칙 목록 맨 앞에 “첫 도구 호출은 반드시 그래프다”라고 박아 두니 그제야 쓰기 시작했는데, 그러고도 실행당 1~4번이었어요.

Claude Code 2.1.163 얘기도 해야겠네요. 이 버전은 --mcp-config로 넘긴 MCP 서버를 비동기로 연결해요. 서버가 뜨기 전에 첫 턴이 시작돼서 도구 목록에 아예 안 잡히더라고요. 첫 A/B는 이것 때문에 켠 조건이 무효였어요. 환경변수 MCP_CONNECTION_NONBLOCKING=false를 주거나 서버 설정에 "alwaysLoad": true를 넣으면 연결을 기다려 줘요.

Serena는 --mode를 쉼표로 이어 넘기면 그 문자열 전체를 모드 이름으로 찾다가 죽어요. 플래그를 반복해서 넘겨야 해요. 읽기 전용은 프로젝트 설정의 read_only: true랑 excluded_tools로 잠갔어요.

검색은 병목이 아니었어요

이번 질문 유형에서는 파일 읽기와 문자열 검색만으로 핵심 파일을 다 찾고 있었어요. 답이 아쉬웠다면 검색이 아니라 그 뒤 합성 단계나 기획 문서 쪽 근거를 봐야 했던 거죠. 그래프가 빛날 질문은 “이 함수 바꾸면 영향 범위가 어디까지냐” 같은 관계 추적형인데, 아직 그런 질문이 들어온 적이 없어요. 나중에 그런 질문이 들어와서 틀리기 시작하면 그때 다시 붙여서 같은 방식으로 비교하면 돼요. 그때 후보는 Serena예요. 언어 서버가 참조를 찾아서 추론으로 만든 엣지가 없고, 설치도 명령 한 줄에 언어 서버까지 알아서 깔렸거든요.
