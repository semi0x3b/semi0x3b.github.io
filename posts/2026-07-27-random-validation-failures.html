같은 데이터인데 매번 다른 필드에서 검증이 실패했어요

2026년 7월 27일7 min read

지난주에 사내 LMS의 지원서 조회 API가 이상한 에러를 뱉기 시작했어요. 같은 코드, 같은 데이터인데 호출할 때마다 다른 필드에서 검증 에러가 났거든요.

{"success": false, "message": "ValueError: no valid value found for dictionary value @ data['depth']"}
{"success": false, "message": "ValueError: not a valid value for dictionary value @ data['ai_review_info']"}
{"success": false, "message": "ValueError: no valid value found for dictionary value @ data['id']"}

더 이상한 건 서버마다 달랐다는 거예요. 어드민 서버가 두 대 있는데 둘 다 같은 코드로 떠 있어요. 그런데 동시 요청이 많은 쪽에서만 에러가 나고 다른 한쪽은 멀쩡했어요.

용의자는 둘이었어요. 데이터가 이상하거나, 스레드끼리 뭔가를 공유하고 있거나.

데이터부터 배제했어요. 불량 row가 매번 다르게 걸리는 게 아닐까 싶어서 의심 가는 row를 쿼리로 직접 찾아봤는데 한 건도 안 나왔어요. 애초에 이 검증 에러는 필드 값이 스키마 타입에 안 맞을 때 나는 에러인데, depth는 Integer 컬럼이고 id는 String 컬럼이라 DB에서 잘못된 타입이 나올 수가 없고요.

남는 건 스레드가 함께 쓰는 무언가예요. 먼저 리포지토리 인스턴스 공유를 의심했는데 팩토리가 요청마다 새로 만들고 있어서 접었어요. 그래서 DB를 떼고, 이 검증이 실제로 일어나는 엔티티 변환 함수 from_dict만 부하 테스트를 했어요. 스레드 24개가 각자 2,000번씩 같은 정상 데이터를 동시에 넣는 실험이에요. 그랬더니 78건이 실패했는데 실패한 필드도 id, apply_type, resume까지 제각각이었어요. 서버에서 본 증상 그대로였어요.

원인은 검증 스키마를 만드는 한 줄이었어요.

cls.schema는 클래스에 하나뿐인 공유 dict인데, 검증 라이브러리인 voluptuous의 Schema()는 만들어지는 과정에서 넘겨받은 dict를 그 자리에서 고쳐 써요. 그러니까 요청 스레드 여러 개가 같은 dict를 동시에 고쳐 쓰면 서로 반쯤 바뀐 상태를 읽게 돼요. 이렇게 스레드 실행 타이밍이라는 우연에 따라 결과가 달라지는 걸 레이스 컨디션이라고 하는데, 어느 타이밍에 누가 밟히느냐에 따라 실패하는 필드가 매번 달라졌던 거예요.

이러니 이상했던 정황이 전부 설명돼요.

정황설명
같은 DB인데 한쪽 서버만 터짐버그가 DB를 아예 안 타고, 동시 요청이 많은 쪽에서만 레이스가 발동해요
불량 데이터가 없는데 검증 실패데이터가 아니라 메모리의 스키마 dict가 오염

하필 지원서 조회에서 터진 이유도 있어요. 이 API는 한 요청에서 엔티티를 수십~수백 개 만들어서, 레이스에 걸릴 시도 횟수 자체가 다른 데보다 많았거든요.

수정안은 둘을 놓고 테스트했어요. 매 호출 스키마 복사본을 넘기는 안과, 클래스당 한 번만 컴파일해서 재사용하는 안. 재사용 안이 안전한 이유는 dict를 고쳐 쓰는 게 컴파일 순간뿐이라서예요. 아직 스레드가 하나뿐인 import 시점에 한 번만 컴파일해두면, 그 뒤로는 완성된 Schema를 쓰기만 하거든요. 둘 다 24스레드에서 에러 0건이었는데 deepcopy 쪽을 골랐어요. 기존 코드가 어차피 매 호출 Schema를 새로 만들고 있어서, 동작은 그대로 두고 비용만 deepcopy 하나 얹는 최소 변경이거든요.

고치고 나서 세 가지를 확인했어요. 같은 부하 테스트를 다시 돌려 에러 0건인 것, 불량 데이터(이상한 status 값 같은)는 여전히 거부하는 것, 그리고 이 실험을 24스레드 동시 호출 회귀 테스트로 만들어 CI에 남긴 것.

덤도 있었어요. from_dict가 들어 있는 mixin(여러 클래스가 물려받는 공통 구현)이 거의 모든 도메인 엔티티의 베이스라서, 수정 하나로 전 도메인이 같이 고쳐졌어요.

다음부터는 클래스 변수처럼 공유되는 걸 외부 라이브러리에 넘길 때 일단 복사본부터 주려고요. 함수가 넘겨받은 인자를 변형하는지는 문서에 잘 안 나오거든요.
